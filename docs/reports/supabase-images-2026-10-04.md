# نقل صور المتجر إلى Supabase — 2026-10-04

## الحالة المؤكدة

صورة الخطأ تخص حساب Cloudinary: استهلاك 30.04 رصيدًا مقابل حصة 25 خلال 30 يومًا. لا تكفي لإثبات توقف استضافة الموقع أو وجود هجوم. تعطّل مزوّد الصور يفسّر عدم ظهور الصور المعتمدة عليه.

الفحص المباشر للقراءة فقط وجد 151 مرجعًا في معرض المنتجات، و86 صورة غلاف للألوان، و738 مرجعًا في عناصر الطلبات: **975 مرجعًا إلى 167 رابط صورة مختلفًا**. عينات التنزيل العام وواجهة إدارة Cloudinary أعادت HTTP 401. أداة التحضير توقف محاولة تنزيل بقية صور الحساب بعد رفض الوصول، ولا تستبدل صور المنتجات بصورة الخطأ التي يعيدها المزوّد.

سكربت النقل القديم إلى Cloudinary لم يحذف أصول Supabase، لكنه لم يحتفظ بخريطة تربط كل رابط جديد بالملف الأصلي. لا يجوز تخمين هذه العلاقة بترتيب أسماء الملفات، خصوصًا بعد حذف/إعادة إنشاء ألوان المنتجات.

الجرد الكامل لمخزن `product-images` وجد **139 ملفًا** بحجم إجمالي نحو **86.9 MiB**. منها 59 ملفًا داخل مجلدات منتجات ما زالت موجودة، و20 ملفًا تطابق مجلداتها معرّفات 6 ألوان حالية. بقية الملفات قد تخص منتجات أو ألوانًا قديمة؛ لا يعني العدد أن كل صور المتجر الحالية مستعادة. خريطة الجرد محلية في `.local/image-migration/all-originals-inventory.json`، ومعاينة الأصول في `.local/image-migration/recovered-originals.html`.

تم تنزيل الملفات الـ139 والتحقق من استجابتها وتنسيقها وحفظ بصماتها محليًا. يوجد بينها تكرار: **62 صورة فريدة بحسب SHA-256**. النسخة المحلية في `.local/image-migration/recovered` لا تعدّل الملفات الأصلية أو أي مرجع حي. المعاينة تجمع الصور تحت معرّفات مجلداتها؛ أسماء المنتجات الحالية لا تضمن أن كل صورة قديمة ما زالت مناسبة للمنتج بعد تعديل بياناته.

## التغييرات المحلية

- مسار `/api/admin/images/upload` يرفع إلى مخزن Supabase عام باسم `catalog-images` بعد التحقق من جلسة المسؤول ومعرّفات المنتج واللون.
- المخزن يُنشأ تلقائيًا عند أول رفع فعلي إن لم يكن موجودًا. لا يحوّل مخزنًا خاصًا إلى عام ولا يضيف سياسات كتابة عامة؛ الرفع بالخادم عبر مفتاح الخدمة.
- يقبل JPEG وPNG وWebP وGIF، ويتحقق من توقيع التنسيق بدل الثقة بامتداد الملف أو MIME المرسل. الحد 4 MiB، وأسماء الملفات فريدة مع تخزين مؤقت لمدة سنة.
- ضغط المتصفح يستهدف 700 KiB وأقصى بعد 1600 بكسل. هذا هدف ضغط وليس ضمانًا لحجم كل صورة؛ الخادم يرفض تجاوز الحد الأعلى.
- أبقينا المسار القديم `/api/admin/cloudinary/upload` متوافقًا مع التبويبات المفتوحة، وأصبح يرفع إلى Supabase أيضًا.
- الشعار وصورة الواجهة يستخدمان `/logo.png` و`/pogo.png` الموجودين في المشروع.
- بقي السماح بعرض روابط Cloudinary القديمة في إعدادات الصور وCSP حتى ينتهي النقل.

**هذه تغييرات في المشروع المحلي. لا تعني أن النسخة المنشورة تغيّرت أو أن الصور نُقلت إلى مخزن جديد بالفعل.** لم تُحذف أصول، ولم تُعدّل روابط قاعدة البيانات أو الفوترة.

## النقل القابل للمراجعة والاستئناف

```bash
npm run migrate:supabase -- --prepare
```

الافتراضي هو التحضير فقط: قراءة المراجع على صفحات، تنزيل الملفات المتاحة إلى `.local/image-migration/files`، وتسجيل بصمتها ومراجعها في `.local/image-migration/plan.json`. هذا المجلد مستثنى من Git. لا توجد مفاتيح خدمة أو بيانات أسماء/هواتف العملاء في الخطة.

حصيلة التحضير الأول: 167 صورة غير جاهزة للنقل بسبب تعذّر الوصول إلى المصدر. لذلك **يرفض أمر التطبيق العمل الآن**. لا يحفظ روابط جديدة لصور لم يستطع تنزيلها.

عند استعادة الوصول إلى Cloudinary، يُعاد أمر التحضير. وللأصول الموجودة يدويًا يمكن إنشاء ملف JSON يربط كل رابط Cloudinary كاملًا بالصورة المطابقة بعد مراجعتها:

```json
{
  "https://res.cloudinary.com/YOUR_CLOUD/image/upload/EXACT_IMAGE.jpg": "/absolute/path/to/the-matching-original.jpg"
}
```

يُقبل أيضًا رابط عام إلى صورة داخل Storage في مشروع Supabase نفسه. لا تُستخدم صورة بديلة لمجرد أنها في مجلد المنتج نفسه.

```bash
npm run migrate:supabase -- --prepare --map=.local/image-migration/overrides.json
```

بعد جاهزية جميع الصور ومراجعة الخطة:

```bash
npm run migrate:supabase -- --apply
```

يتحقق التطبيق من ملفات التحضير، ثم يرفعها بأسماء تعتمد على SHA-256 دون الكتابة فوق الملفات الموجودة، وينزّل النسخ العامة لمطابقة البصمات **قبل أول تعديل لقاعدة البيانات**. يحفظ كل مرجع بشرط أن رابطَه القديم لم يتغيّر؛ لا يمحو تعديلات المسؤول المتزامنة. أي تعارض يُسجّل في الخطة ويجعل الأمر ينتهي بخطأ.

تحديث المراجع يتم على خطوات قابلة للاستئناف، وليس في معاملة واحدة تشمل كل الجداول. عند انقطاع العملية يُعاد `--apply` بالخطة نفسها. لا يُعاد `--prepare` فوق خطة بدأ تطبيقها؛ استخدم `--plan=PATH` آخر لجرد جديد. يحتفظ الملف الأصلي بالمعلومات اللازمة للتراجع:

```bash
npm run migrate:supabase -- --rollback
```

التراجع يغيّر فقط المراجع التي ما زالت تشير إلى وجهة هذه الخطة، ولا يحذف الصور. يعيد روابط Cloudinary القديمة حتى لو كان حساب Cloudinary ما زال معطّلًا، لذلك يُستخدم فقط عند الحاجة للتراجع عن نقل خاطئ.

بعد التطبيق/التراجع يجب تحديث ذاكرة المتجر المؤقتة عبر `POST /api/admin/store-cache` من جلسة المسؤول، والتحقق من المعرض والأغلفة وصور عناصر الطلبات. يجب نشر تغييرات الكود ليصبح رفع الصور الجديدة والشعار وصورة الواجهة مستقلًا عن Cloudinary في النسخة الحية.

## خطة Pro

بحسب [تسعير Supabase الرسمي](https://supabase.com/pricing)، تتضمن Pro حاليًا 100 GB لتخزين الملفات، و250 GB من Egress، و250 GB منفصلة من Cached Egress. ليست غير محدودة. يجب مراقبة الاستهلاك وضغط الصور والاستفادة من التخزين المؤقت. لم يتم تعطيل Spend Cap أو تفعيل أي خدمات إضافية مدفوعة.

## التحقق

- `npm run test:images`: نجح. يغطي صلاحيات الرفع، الأنواع والأحجام والأخطاء، عدم قبول صورة خطأ HTTP، جرد الصفحات، عزل المشروع، عدم الكتابة فوق التعديلات المتزامنة والتراجع.
- `npm run test:admin`: نجح.
- `npx tsc --noEmit`: نجح.
- `npm run build`: نجح، بما فيه توليد الصفحات والتحقق من TypeScript ومسار الرفع الجديد.
- ESLint للملفات الجديدة ومسار الرفع المتوافق: نجح.
- فحص مكونات العرض المعدّلة أظهر خطأً موجودًا مسبقًا في `Header.tsx` متعلقًا بـ `setMounted` داخل effect، وتحذيرات قديمة. تعديل الشعار اقتصر على الرابط.

لم يُجرَ رفع تجريبي إلى الإنتاج أو تطبيق لخطة النقل. نجاح الاختبارات المحلية لا يُثبت اكتمال نقل الصور الحية.
