# تصحيح إجمالي الطلب عند تغيير المنتجات — 2026-10-07

كان نموذج تعديل الطلب يحتفظ بـ `total_price` في حالة مستقلة عن المنتجات. إضافة منتج أو تغيير كميته كانت تحدّث مجموع الكتالوج فقط، بينما الحفظ يرسل الإجمالي القديم باعتباره سعرًا يدويًا. أُعيد إنتاج الحالة باختبار للنموذج: إجمالي 6750 دج بقي 6750 بدل 7950 بعد إضافة منتج بسعر 1200 دج.

أصبح المبلغ المدخل مرتبطًا بمجموع المنتجات لحظة إدخاله. أي تغيير لاحق في المنتجات يضيف أو يطرح فرق السعر تلقائيًا. يبقى التخفيض أو الزيادة اليدوية **مبلغًا ثابتًا**؛ مثلًا تخفيض 550 دج يستمر عند إضافة منتج، لكن الإجمالي نفسه لا يبقى ثابتًا. مجرد فتح الطلب وحفظه لا يعيد تسعير المبلغ المحفوظ.

يشمل ذلك الإضافة والحذف واستبدال المنتج وتغيير الكمية. تغيير رسوم التوصيل أو تفعيل التوصيل المجاني يستخدم الإجمالي المحدّث. زر استخدام المبلغ المحسوب يلغي التعديل اليدوي ويعيد السعر المحسوب للمنتجات والتوصيل. الحساب بفئات السنتيم لتجنّب أخطاء جمع الكسور. المبلغ الفارغ أو غير الصالح لا يتحوّل ضمنيًا إلى مبلغ قابل للحفظ؛ إذا جعل حذف المنتجات السعر أقل من رسوم التوصيل، يجب تصحيحه قبل الحفظ.

التحقق:

- اختبار النموذج فشل على النسخة القديمة: `6750 !== 7950`، ثم نجح بعد الإصلاح.
- `npm run test:admin`: نجح، بما يشمل سيناريوهات الإضافة والحذف والكميات والاستبدال والتخفيضات والتوصيل والكسور ومبلغ الحفظ.
- اختبار API يتحقق من إرسال مبلغ طلب يحتوي منتجًا ثانيًا إلى RPC، وإلى مسودة Ecotrack للطلب المؤكد. الاتصالات في الاختبارات محاكاة؛ لم تُعدّل طلبات حقيقية.
- `npx tsc --noEmit` وESLint لملفات التنفيذ المعدّلة واختبار الواجهة: نجحت.

لا يتطلب التصحيح ترحيل SQL، ويتطلب نشر نسخة التطبيق وتحديث التبويبات المفتوحة. الطلبات التي حُفظت سابقًا بسعر خاطئ تحتاج مراجعة؛ لا يمكن تمييزها تلقائيًا عن التخفيضات المقصودة بمجرد مقارنة الإجمالي بأسعار الكتالوج الحالية.
