> Investigate the recurring order-restoration failure end to end. Trace the admin UI, API, database functions, stock handling, and operation locks. Reproduce the failure, identify its root causes, and fix them without bypassing stock checks or changing live orders blindly.

## الأسباب

1. دالة الاسترجاع القديمة ترفض أي عنصر فقد مرجع اللون أو المقاس، حتى عندما يوجد تطابق وحيد صالح داخل المنتج. أُعيد إنتاج هذا الفشل على PostgreSQL محلي باستخدام الدالة القديمة نفسها.
2. علاقات `order_items` تستخدم `ON DELETE SET NULL`. كان حذف مقاس أو لون مرتبط بطلب قديم يمحو مرجعه، بما في ذلك الطلبات الموجودة في المحذوفات. هذا مسار مثبت في بنية القاعدة، ولا يحدد تاريخ فقدان كل مرجع موجود حاليًا.
3. مسار الرجوع `restoreUnlimitedStockOrder` كان يجري قراءات متفرقة ثم يلغي حذف الطلب مباشرة، خارج معاملة فحص المخزون وحجزه. أُزيل بالكامل.
4. الواجهة كانت تستبدل حالة الطلب محليًا بـ`pending` بدل اعتماد بيانات الخادم، حتى في بعض حالات إعادة المحاولة، وتعرض أخطاء عامة قصيرة العمر.
5. غياب عناصر الطلب، والكميات غير الصحيحة، وتكرار التركيبة داخل الطلب، وإعادة المحاولة المتزامنة احتاجت تحققًا واختبارات صريحة.

## الإصلاح المنفذ

- دالة `restore_order_safely` تقفل الطلب وتفحص العناصر وتصلح الروابط وتحجز المخزون وتسترجع الطلب ضمن معاملة واحدة. أي استثناء يعيد جميع التغييرات.
- الربط التلقائي يقتصر على مرجع لون أو مقاس مفقود وله تطابق وحيد بالاسم داخل المنتج نفسه، مع تجاهل حالة الأحرف والمسافات الطرفية. لا تختار الدالة منتجًا بالاسم، ولا تختار بين تطابقات متعددة.
- عند غياب تطابق أو نقص المخزون تظهر نافذة مراجعة داخل اللوحة، بالمنتج واللون والمقاس والكمية الأصلية، وتتيح اختيار البدائل صراحةً. تبقى الكميات والإجمالي المتفق عليه ثابتين.
- اختيارات الإصلاح اليدوي مرتبطة بنسخة الطلب؛ تُرفض إذا تغيّر الطلب قبل الحفظ. يتحقق الخادم من انتماء كل عنصر إلى الطلب، وكل لون ومقاس إلى المنتج المختار.
- يُجمع طلب المخزون للتركيبات المكررة. تُقفل التركيبات بالآلية نفسها المستخدمة في تعديل المخزون، بما فيها التركيبة التي لا سجل لها. غياب سجل التركيبة يعني مخزونًا غير محدود؛ الصفر يمنع الحجز.
- إعادة محاولة استرجاع طلب نشط تُرجع حالته الحالية دون حجز ثانٍ أو إعادته من مؤكد إلى قيد الانتظار. الواجهة تعتمد بيانات الطلب المعادة من الخادم.
- بقي قفل العمليات المشترك مع التعديل والشحن، وبقي تحديث ذاكرة المتجر بعد العملية.
- منع حذف منتج أو لون أو مقاس ما دام مرتبطًا بعنصر طلب، حتى لو كان الطلب مؤرشفًا. يمكن إخفاء الخيار بدل حذفه، ورسالة الحفظ توضّح السبب.
- فُصلت أخطاء نقص المخزون، والخيار المفقود، والطلب المتغير، والعملية المشغولة، والترحيل غير المطبق، وخطأ قاعدة البيانات. الأخطاء التي تتطلب معالجة لا تختفي باختفاء إشعار مؤقت.

## التحقق

- نجحت `npm run test:admin`، وتشمل سلوك نافذة اختيار البديل، عدم اختيار مقاس مفقود تلقائيًا في النموذج، إرسال الاختيارات والنسخة، معالجة أخطاء API وصلاحياته، ومنع الرجوع إلى تحديثات متفرقة.
- نجحت اختبارات PostgreSQL المؤقتة عبر `bash scripts/tests/run-admin-db-tests.sh`: إعادة إنتاج الفشل القديم، التطابق الوحيد والمتعدد والمفقود، الإصلاح اليدوي، رفض النسخة القديمة والعنصر الأجنبي، المخزون المحدود وغير المحدود والصفر، مجموع التركيبات المكررة، الطلب الفارغ والكميات السالبة، صلاحيات الدوال، ومنع حذف الخيارات المرتبطة.
- نجح اختبار حقن فشل بعد تعديل المخزون للتأكد من التراجع الكامل، واختبار الحذف ثم الاسترجاع للتأكد من توازن المخزون.
- نجح اختبار اتصالين حقيقيين متزامنين لاسترجاع الطلب نفسه: الحجز مرة واحدة، والمحاولة الثانية ترجع `already_restored`.
- نجح TypeScript، وفحص ESLint للملفات المعدلة دون أخطاء؛ بقي تحذيران موجودان لاستخدام `img` في صفحة الطلبات.
- نجح بناء الإنتاج `npm run build` بما فيه توليد الصفحات. لم يُجر اختبار تفاعلي في متصفح متصل ببيانات الإنتاج، ولم يُنشأ أو يُرسل طلب شحن حقيقي.
