**التغييرات المنفذة**

- أصبح حفظ المنتج والألوان والصور والمقاسات وتغييرات المخزون معاملة PostgreSQL واحدة عبر `save_catalog_product`. فشل أي خطوة يعيد جميع تغييرات قاعدة البيانات؛ أخطاء الحفظ تظهر في النموذج.
- لا يرسل نموذج المنتج المخزون الذي لم يتغير. التعديل المقصود على خانة يتحقق من قيمتها السابقة تحت قفل صف، ويرفض الحفظ إذا سبقته عملية حجز أو تعديل آخر. صفحة المخزون تستخدم التحقق نفسه.
- الخانة الفارغة تحذف سجل التركيبة، وهو تمثيل المخزون غير المحدود. الصفر يبقى كمية صفرية، ولا تُنشأ سجلات صفرية للخانات غير المعدلة.
- يُرفض حفظ منتج من نافذة قديمة باستخدام `updated_at`. نافذة الطلب تجلب أحدث بيانات عند فتحها وتفحص تغيّر قيم الحقول نفسها عند الحفظ؛ تغيير وقت التحديث وحده لا يمنع الحفظ. عند تعارض فعلي تعرض القيم الأحدث وتحافظ على المدخلات وتتيح الحفظ بعد مراجعتها صراحةً. تبقى حماية الطلبات المرسلة والمحذوفة سارية.
- تشترك عمليات تعديل الطلب، التأكيد، الاسترجاع، الحذف، وإنشاء/حذف/إرسال بوليصة Ecotrack في قفل محفوظ بقاعدة البيانات لكل طلب. يشمل القفل فترة الاتصال الخارجي والتراجع عند فشل حفظ الطلب، ويعمل عبر أكثر من خادم.
- تقرأ المزامنة النسخة المحلية قبل جلب البيانات الخارجية. تُطبّق النتيجة فقط إذا لم يتغير تاريخ التحديث أو رقم التتبع، ولم يُحذف الطلب، ولم تكن هناك عملية أخرى عليه. لا تعيد لقطة قديمة طلبًا مُسلّمًا إلى مؤكد.
- حفظ الإعدادات يفحص نتيجة الخادم ويعرض الخطأ، ويعيد حالة زر الحفظ دائمًا، ولا يعرض النجاح عند الفشل.
- مبالغ المقارنة الشهرية، ومتوسط الطلب، وترتيب المنتجات المباعة والولايات حسب قيمة المبيعات تعتمد على الطلبات المُسلّمة فقط. مؤشرات أعداد الطلبات وحالاتها تشمل كل الحالات. تم ضبط حدود الرسم اليومي إلى 30 نقطة، وإزالة الربط الداخلي الذي يستبعد طلبًا بلا عناصر من الإحصاءات.
- جميع تغييرات الكتالوج تمر عبر مسار إدارة يتحقق من صلاحية المسؤول ويحدث ذاكرة صفحات المتجر بعد نجاح قاعدة البيانات: المنتجات، الظهور، الحذف، التصنيفات، المخزون، التقييمات وسياسة المتجر. إنشاء الطلب وتعديله وحذفه واسترجاعه يحدث ذاكرة المخزون أيضًا.

**التطبيق على قاعدة البيانات**

طبّق الملفين التاليين بالترتيب، بعد الترحيلات الموجودة، ثم انشر نسخة التطبيق الجديدة مع إعادة تحميل صفحات الإدارة المفتوحة:

1. `supabase/migrations/20260928130000_atomic_catalog_save.sql`
2. `supabase/migrations/20260928131000_serialize_order_operations.sql`

هذه الترحيلات اختُبرت على PostgreSQL محلي مؤقت. لم تُطبق على قاعدة المتجر الفعلية ضمن هذا العمل. يجب تنسيق النشر بحيث لا تعمل النسخة القديمة بالتزامن مع الجديدة: النسخة القديمة لا تستخدم قفل العمليات ولا مسار الحفظ الجديد.

الدوال الجديدة تمنح التنفيذ إلى `service_role` فقط؛ يستدعيها الخادم بعد التحقق من المسؤول. لا توجد آلية رجوع إلى الحفظ القديم عند غياب الترحيلات، حتى لا يُعاد إدخال مشكلة التزامن بصمت.

**استعادة قفل بعد توقف الخادم قسرًا**

لا تنتهي صلاحية القفل تلقائيًا؛ حذف قفل عملية بطيئة اعتمادًا على الوقت وحده قد يسمح بإرسال الطلب وتعديله بالتزامن. يزيل الخادم القفل في `finally` في المسارات العادية، بما فيها أخطاء التحقق والخدمات. إذا أُوقفت العملية قسرًا أو فشل تحرير القفل، يظهر في سجل الخادم `Order lock requires recovery` عند فشل التحرير.

يمكن للمشرف الفني مراجعة الأقفال من SQL Editor:

```sql
select order_id, token, started_at
from public.order_operation_locks
order by started_at;
```

قبل تحرير قفل متبقٍ، تأكد من انتهاء العامل القديم، ثم طابق حالة الطلب ومبلغ البوليصة مع Ecotrack وعالج أي اختلاف. حرّر القفل المحدد باستدعاء `public.release_order_operation` باستخدام `order_id` و`token` المقروءين؛ لا تحذف الأقفال بالجملة أو حسب العمر فقط.

**حدود المعاملة الخارجية**

المعاملة الواحدة تشمل جداول PostgreSQL. يُرفع الملف إلى Cloudinary قبل المعاملة، وتُعاد الاستفادة من الرفع الناجح عند إعادة المحاولة في النافذة نفسها. لا تستطيع PostgreSQL التراجع عن ملف رُفع خارجيًا؛ قد يبقى ملف غير مرتبط إذا أُغلق النموذج بعد فشل الحفظ.

القفل يمنع عمليات التطبيق المتزامنة على الطلب نفسه، لكنه لا يجعل Ecotrack وPostgreSQL معاملة موزعة. انقطاع الاتصال أو فشل التراجع الخارجي ما زال يحتاج مطابقة مع شركة التوصيل. التعديلات المباشرة في لوحة Ecotrack أو SQL Editor تقع خارج قفل التطبيق.

إذا فشل تحديث ذاكرة المتجر بعد نجاح الحفظ، تعرض اللوحة تحذيرًا يميز نجاح حفظ البيانات عن تأخر ظهورها؛ لا تعيد تنفيذ الحفظ على أنه فشل.

**الاختبارات**

- `npm run test:admin`: اختبارات سلوك النماذج، أخطاء الإعدادات، الحسابات المالية، تحديث الكاش لكل نوع تعديل، صلاحيات مسار الكتالوج، منع تداخل التعديل والشحن، ورفض نافذة الطلب القديمة. تشمل أيضًا اختبارات تعديل الإجمالي والتوصيل المجاني والتراجع عن تعديل مبلغ Ecotrack.
- `npm run test:admin:db`: ينشئ قاعدة PostgreSQL مؤقتة، ويختبر المعاملة كاملة، والتراجع بعد فشل الصور/المخزون، والخانة الفارغة والصفر، والصلاحيات، والأقفال، وتجاهل المزامنة القديمة أو المتعارضة. يتضمن اختبار اتصالين متزامنين لحجز مخزون وحفظ قيمة قديمة. يحذف قاعدة الاختبار بعد الانتهاء.
- اختبارات Ecotrack تستخدم محاكاة؛ لا تُنشئ أو تُرسل بوليصة حقيقية.
- تشمل اختبارات تعديل الطلب تحديث وقت الحفظ وحده، واختلاف صيغة المنطقة الزمنية، والتعارض الحقيقي قبل الاتصال بـEcotrack، وحفظ المدخلات بعد مراجعة القيم الأحدث. اختُبر بقاء الإجمالي المدخل في النافذة عند التعارض. هذا التصحيح اللاحق لا يحتاج ترحيل SQL إضافيًا؛ يُنشر مع نسخة التطبيق.

لتغيير مكان أدوات PostgreSQL المحلية يمكن ضبط `PG_BIN` قبل تشغيل اختبار قاعدة البيانات؛ القيمة الافتراضية `/usr/lib/postgresql/17/bin`.

نجحت اختبارات التطبيق وقاعدة البيانات المذكورة أعلاه. تعذّر إكمال `npm run build` بسبب فشل تحميل Google Fonts ضمن قيود الاتصال. رفضت المراجعة التلقائية طلب إعادة البناء مع اتصال خارجي بسبب بلوغ حد الاستخدام؛ لذلك لا يُعدّ بناء الإنتاج متحققًا، ويجب تشغيله في بيئة تسمح بتحميل الخطوط قبل النشر.
