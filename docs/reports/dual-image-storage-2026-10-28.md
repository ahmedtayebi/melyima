# نسختان لصور المنتجات مع بديل تلقائي — 2026-10-28

المطلوب: حفظ كل صورة منتج جديدة في Supabase، ورفع نسخة منها إلى Cloudinary ليكون مصدر العرض الأساسي، واستخدام Supabase عند فشل تحميل Cloudinary. هذا يحل محل مسار Supabase فقط الذي أُعدّ في 2026-10-04.

## الرفع

1. يجهّز المتصفح الصورة ثم يرسلها إلى `/api/admin/images/upload` عند حفظ المنتج.
2. يتحقق الخادم من جلسة المسؤول والصورة، ويحفظ الملف في `catalog-images/products/<product>/<color>/<uuid>.<extension>` بأسماء فريدة دون الكتابة فوق ملف سابق.
3. بعد نجاح حفظ Supabase، يرفع الخادم البايتات نفسها إلى Cloudinary بطلب موقّع، مع مهلة 15 ثانية ودون اتباع تحويلات HTTP. مفاتيح Cloudinary تبقى في الخادم.
4. عند نجاح النسختين، يُعاد رابط Cloudinary المحسّن ليُحفظ في حقول الصور الحالية. إذا فشل Cloudinary، يُعاد رابط Supabase ويظهر تنبيه للمسؤول بعد حفظ المنتج. لا ندّعي وجود النسخة الثانية في هذه الحالة، ولا توجد مهمة خلفية تعيد رفعها تلقائيًا لاحقًا.
5. إذا فشل حفظ Supabase، يفشل الرفع ولا تبدأ محاولة Cloudinary؛ لا تُنشأ صورة جديدة تعتمد وحدها على Cloudinary.

تستخدم النسخة الثانية معرّفًا ثابت البنية:

```text
melyima/supabase-v1/<supabase-host>/catalog-images/<original-extension>/products/<product>/<color>/<uuid>
```

يسمح ذلك باستخراج رابط النسخة الأصلية المطابقة من رابط Cloudinary نفسه، بما في ذلك الروابط المخزّنة في السلة والطلبات. يحفظ الامتداد الأصلي حتى إذا قدّم Cloudinary تنسيقًا آخر. نتحقق من تطابق المشروع والمسار ومعرّفات UUID ومن أن استجابة الرفع تخص الصورة المطلوبة. لا يلزم تغيير مخطط قاعدة البيانات أو طلب API إضافي لكل صورة عند تعطل Cloudinary. يجب الحفاظ على هذه البنية عند إدارة ملفات النسخ الجديدة في Cloudinary.

## العرض

`components/ui/ProductImage.tsx` يوفّر نسختين للمكوّن: صورة HTML عادية وصورة Next.js. كلتاهما تعرض Cloudinary أولًا ثم تبدّل المصدر إلى Supabase عند خطأ التحميل، أو صورة خطأ بحجم بكسل واحد. يعالج أيضًا فشل الصورة قبل ربط أحداث React عند تحميل الصفحة. يتوقف التبديل عند Supabase ولا ينشئ حلقة محاولات إذا فشل المصدران. تغيير المنتج/اللون/الصورة يبدأ دورة جديدة للصورة الجديدة.

تم توصيل المكوّن ببطاقات المنتجات، معرض المنتج للهاتف والكمبيوتر والصور المصغّرة، السلة، صور الطلبات في اللوحة، قائمة المنتجات والمخزون ومعاينة صور نموذج المنتج. العرض مباشر دون تمرير الصورة عبر محسّن Next.js. صور المشاركة وبيانات المنتج لمحركات البحث تستخدم نسخة Supabase المعروفة لأن قارئها قد لا يشغّل أحداث المتصفح.

التبديل يعتمد على فشل تحميل الصورة، وليس على استعلام رصيد Cloudinary مع كل زيارة. التحويل داخل المتصفح لا يغيّر رابط قاعدة البيانات.

## الحدود والنشر

- يتطلب نشر الكود وإعداد `CLOUDINARY_CLOUD_NAME` و`CLOUDINARY_API_KEY` و`CLOUDINARY_API_SECRET` في الخادم، مع إعدادات Supabase الحالية.
- الروابط القديمة في Cloudinary لا تتضمن خريطة مؤكدة إلى نسخة أخرى، لذلك لا تُمنح بدائل تخمينية. الصور المخزّنة مسبقًا في Supabase تستمر في العرض مباشرة حتى تُنسخ إلى Cloudinary بعملية منفصلة.
- الصور المحلية، مثل الشعار، وصور المراجعات لم تتغيّر.
- تُرفع الملفات قبل معاملة حفظ المنتج. قد تبقى ملفات غير مرتبطة إذا فشل حفظ بيانات المنتج أو أُلغي، كما في المسار السابق. لم تُضف عمليات حذف للأصول.
- لم تُعدّل صور أو روابط الإنتاج ولم تُنفّذ ترقية أو تغييرات فوترة.

## نسخ الصور الجديدة الموجودة مسبقًا في Supabase

أضيف `scripts/mirror-supabase-images-to-cloudinary.mjs`، ويُشغَّل من مجلد المشروع المحلي الذي يحتوي على `.env.local`. يستخدم أدوات الرفع وتحديد النسخة الاحتياطية نفسها التي يستخدمها الموقع. الملفات المشتركة بصيغة `.mjs` لكي يعمل الأمر مع Node.js 20 دون أداة تحويل TypeScript إضافية.

1. انشر أولًا تغييرات الرفع المزدوج ومكوّن الرجوع إلى Supabase. تأكد من وجود إعدادات Supabase ومفاتيح Cloudinary في `.env.local`، ومن أن حساب Cloudinary يقبل الرفع والعرض.
2. افحص الصور دون تنزيلها أو رفعها أو تغيير قاعدة البيانات:

   ```bash
   npm run images:mirror -- --dry-run
   ```

3. انسخ الصور وغيّر روابطها بعد التحقق:

   ```bash
   npm run images:mirror -- --apply
   ```

4. حدّث ذاكرة صفحات المتجر. وأنت مسجّل الدخول كمسؤول، افتح Console في أدوات المطور على موقع المتجر وشغّل:

   ```js
   const response = await fetch('/api/admin/store-cache', { method: 'POST' });
   const result = await response.json();
   if (!response.ok || !result.success) throw new Error(result.error || 'تعذّر تحديث الصفحات');
   console.log('تم تحديث صفحات المتجر');
   ```

   ثم أعد تحميل صفحة المنتج وتحقق من صور المعرض واللون والطلب. لا يحتاج هذا الطلب إلى نسخ مفاتيح سرية إلى المتصفح؛ يستخدم جلسة المسؤول الحالية.

الأمر يستهدف روابط مشروعك فقط في `catalog-images/products/<product>/<color>/<uuid>.<extension>` داخل صور المعرض وصورة اللون وصور عناصر الطلبات. لا ينسخ الملفات غير المرتبطة بقاعدة البيانات، ولا الصور المحلية أو روابط Cloudinary الحالية أو المسارات القديمة `product-images` و`catalog-images/migrated`. عدد الصور الفريدة يختلف عن عدد المراجع لأن الصورة قد تظهر في عدة حقول.

كل ملف يُنسخ مرة بمعرّف ثابت دون استبدال ملف موجود في Cloudinary. تُنزّل نسخة Cloudinary الأصلية ويُقارن SHA-256 مع ملف Supabase قبل أي تغيير لروابط تلك الصورة. عند فشل الرفع أو التحقق تتوقف العملية، وتبقى روابط الصورة المتعذرة كما كانت؛ النسخ الناجحة السابقة تبقى محفوظة. تغييرات الروابط تستخدم مقارنة القيمة القديمة، فلا تستبدل تعديلًا أحدث أجراه المسؤول. التعارضات تسجّل ويخرج الأمر برمز فشل.

تُحفظ خريطة الروابط والتقدّم محليًا في `.local/image-mirror/state.json`، خارج Git. احتفظ بها؛ إعادة أمر `--apply` تستأنف العمل وتضيف المراجع الجديدة دون إعادة رفع الصور المسجلة. يتحقق الأمر من المشروع وحساب Cloudinary ومن أن الأصل في Supabase لم يتغير. يُمنع تشغيل نسختين من الأمر بالتزامن بواسطة `run.lock`. إذا أُغلق الجهاز أثناء التشغيل، احذف مجلد القفل الفارغ فقط بعد التأكد من عدم وجود عملية أخرى؛ لا تحذف `state.json`.

للرجوع إلى روابط Supabase المسجلة في الخريطة، دون حذف أي صورة من الخدمتين:

```bash
npm run images:mirror -- --rollback
```

حدّث ذاكرة المتجر بعد الرجوع أيضًا. لا تُستبدل تعديلات المسؤول المتزامنة أثناء الرجوع. أصبح `npm run migrate:cloudinary` اسمًا بديلًا للأمر الآمن الجديد؛ لا تستخدم ملف الترحيل التاريخي `scripts/migrate-supabase-images-to-cloudinary.mjs` مباشرة، فهو مخصص للمسار القديم ولا ينشئ علاقة النسخة الاحتياطية الحالية.
